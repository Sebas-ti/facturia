## Decisiones tomadas
- 2026-09-30 — Se agregan los códigos `INVALID_CUFE` (ALTA) e `INCOHERENT_DATES` (MEDIA) a `docs/spec.md` §4.1 — el nodo `validate` (§2.1) ya mencionaba validar CUFE y coherencia de fechas pero la tabla de hallazgos no tenía códigos para esos casos.
- 2026-09-30 — `backend/pyproject.toml` usa `[tool.uv] package = false` (proyecto de aplicación, no librería instalable) con `app/` como paquete plano en la raíz de `backend/`, en vez del layout `src/` que genera `uv init` por defecto — así coincide con la estructura de AGENTS.md (`backend/app/...`).
- 2026-09-30 — En esta máquina, `uv run pytest` falla con "Una directiva de Control de aplicaciones bloqueó este archivo" (bloquea `pytest.exe` del venv, no a `ruff`/`mypy`). Workaround: `uv run python -m pytest`. No se cambia el comando en AGENTS.md porque es una política local de Windows, no algo del proyecto.
- 2026-09-30 — `.env.example` lo creó el usuario manualmente (Claude Code tiene una regla de permisos que bloquea `Write`/`Edit` sobre archivos `.env*`, incluido el `.example`); Claude solo entregó el contenido propuesto.
- 2026-09-30 — `docker compose up -d db azurite` sin verificar de extremo a extremo: el CLI y `docker compose config` validan bien, pero justo después de instalar Docker Desktop el motor (`dockerDesktopLinuxEngine`) no respondía todavía. Pendiente que el usuario confirme que los contenedores levantan tras completar el setup inicial de Docker Desktop.
- 2026-09-30 — Docker Desktop ya funciona en esta máquina; `docker compose up -d db azurite` levanta ambos contenedores sin problema (queda resuelto el pendiente anterior).
- 2026-09-30 — La misma política de Control de aplicaciones de Windows que bloqueaba `pytest.exe` también bloquea las extensiones Cython precompiladas (`.pyd`) que trae SQLAlchemy 2.1 en Windows (`_collections_cy`, `_result_cy`, etc., en `engine/`, `sql/` y `util/`). Workaround aplicado en `backend/.venv`: se renombraron esos `.pyd` a `.pyd.disabled`, lo que hace que SQLAlchemy caiga a su fallback puro-Python (los mismos módulos `.py` ya vienen junto a cada `.pyd`). No se toca el proyecto ni `pyproject.toml`; es un ajuste del entorno local (`.venv` se regenera con `uv sync`, así que hay que repetir el workaround si se reinstala).
- 2026-09-30 — `psycopg[binary]` también estaba bloqueado por la misma política, pero ahí no hay fallback puro-Python posible sin `libpq.dll` instalado en el sistema. El usuario instaló PostgreSQL 18 para Windows (solo se necesita `libpq.dll`, no hace falta correr su servicio); se agregó `C:\Program Files\PostgreSQL\18\bin` al PATH de usuario. Documentado en `AGENTS.md` → Comandos.
- 2026-09-30 — `scripts/seed.py` vive en `backend/scripts/` (no en el `scripts/` de la raíz junto a `generate_data.py`) porque necesita importar `app.db.models`/`app.config` y por lo tanto correr con el venv de `backend/` (SQLAlchemy, psycopg). `generate_data.py` es un script independiente sin esa dependencia. Para que `scripts` sea un paquete importable desde los tests se agregó `backend/scripts/__init__.py`.
- 2026-09-30 — El índice único parcial de `invoices(supplier_id, invoice_number)` (spec §5) excluye **todo** `decision = 'RECHAZAR'`, no solo los rechazados por `DUPLICATE_INVOICE` como dice literalmente la spec — la fila de `invoices` no guarda por sí sola qué `Finding` causó el rechazo (eso vive en la tabla `findings`), así que restringir la exclusión a "solo duplicados" no es expresable en un predicado de índice sin una columna adicional. Excluir todo rechazo es un superconjunto seguro: nunca bloquea reinsertar una factura rechazada con el mismo número.
